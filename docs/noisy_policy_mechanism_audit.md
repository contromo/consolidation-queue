Date: 2026-05-15

This audit tests `docs/noisy_policy_mechanism_audit_hypothesis.md` against the
saved 32B Phase 4 noisy policy-comparison artifacts. It adds interpretation

## Audit Thesis

Bucket B is not a broad noisy CQ win. It is a mechanism-local result with one
clean survival row and one partial survival row:

- `forced_contradiction` survives noisy extraction because the 32B output emits
  the contradiction structure CQ needs, and the noisy ablation identifies
  contestation/demotion as the carrying component.
- `preference_drift` partially survives because some standing-preference slots
  remain usable and contradiction edges are intact, but one-off preference text
  often drifts to `temporary_constraint` / `session`, and exact canonical-id
  lookup alignment is only partial.

The exact-tie rows do not all support the stronger extractor-floor convergence
hypothesis. `scope_contamination` has direct 32B evidence of canonicalization,
scope, and contradiction defects. `useful_pending_memory` and
`memory_poisoning`, however, have perfect recorded 32B component scores in the
Phase 4 component artifacts; their noisy policy ties are better recorded as
unattributed nulls consistent with adapter-contract or query-resolution failure
and policy-level no-answer behavior, not as proven reproduction of the 7B
failure taxonomy.

## Cross-Family Pattern: Canonical-Id Alignment

The audit's strongest new diagnostic is policy-facing canonical-id alignment.
This is exact string equality between CQ's extracted candidate `canonical_id`
values and each question trace's `relevant_canonical_id`. It is stricter than
cluster-oriented component scoring, and it explains why some rows can show
strong or perfect 32B component metrics while the policy run still cannot expose
the oracle policy distinction.

| Row | Exact matches | Component readout | Interpretation |
| --- | ---: | --- | --- |
| `forced_contradiction` | `112/120` | perfect 32B components | policy signal mostly survives |
| `preference_drift` | `40/120` | perfect contradiction, residual claim/scope/canonical drift | partial survival |
| `scope_contamination` | `0/75` | residual scope, canonicalization, and contradiction defects | null with 32B defects plus lookup pressure |
| `useful_pending_memory` | `0/60` | perfect 32B components | perfect-component null consistent with adapter-contract or query-resolution failure |
| `memory_poisoning` | `0/60` | perfect 32B components | perfect-component null consistent with adapter-contract or query-resolution failure |
| `false_corroboration` | `0/60` | source identity not extracted | descriptive-only event-source proxy |
| `mechanism_diverse_heldout` | `0/4` | one frozen 32B defect trace | frozen policy tie remains unattributed |

This pattern is not, by itself, proof of semantic extractor failure. It shows a
policy-facing mismatch between the canonical ids the noisy stream emits and the
canonical ids the oracle questions resolve against. Future null-row work should
therefore be preregistered as a canonical-id/query-resolution or adapter-contract
audit before any threshold, prompt, validator, or schema change is considered.

32B behavior: the default 32B component artifact records no scenario errors and
perfect component metrics: candidate F1 `1.00`, claim type `1.00`, scope level

run has `90` true-positive contradiction edges, `0` false negatives, and `0`

## Discussion

The audit narrows the Bucket B contribution.

The strongest publishable claim is not "CQ wins under noisy extraction." It is:
under a preregistered same-candidate-stream noisy comparison, CQ's
contestation/demotion advantage remains visible when the 32B extractor emits
the required contradiction edges. That holds cleanly for
`forced_contradiction`, and partially for `preference_drift`.

The tied rows are scientifically useful, but mostly as diagnostics. Some contain
residual 32B component defects (`scope_contamination`, frozen sentinel). Others
do not (`useful_pending_memory`, `memory_poisoning`). Across the tied rows, a
common policy-facing issue is exact canonical-id/query alignment: the extractor
often emits semantically reasonable slot names that pass clustering-oriented
component evaluation but do not match the oracle query's relevant canonical id,
so lookup fails before policy differences can surface. That is consistent with
adapter-contract or query-resolution failure, but the audit records it as an
open attribution rather than a settled cause.

That distinction matters for the paper. The component gate did real upstream
work by preventing a 7B false unlock, and the mechanism audit does real
downstream work by showing which noisy policy rows remain attributable after the
32B unlock. The answer is mechanism-local: contradiction-edge-driven
contestation survives; broad scope, pending, poisoning, source-independence, and
frozen-sentinel claims remain unsupported under the current noisy stream.

## Follow-Up Implications

- Do not rerun or retune Phase 4 to rescue null rows.
- Do not upgrade `useful_pending_memory` or `memory_poisoning` ties into
  extractor-floor convergence claims without new preregistered evidence.
- If future work addresses the null rows, preregister it as a policy-facing
  canonical-id/query-resolution audit or adapter-contract study, not as a
  threshold sweep that retroactively promotes Bucket B.
- LongMemEval remains gated on this mechanism-local interpretation: only
  contradiction-like update tasks have a supported transfer hypothesis today.
